# Architecture

## Repository layout

```
apps/
  watcher/   Node service: listens to the Kumospace desktop app over CDP and reacts (ntfy). Runs on the Mac via launchd.
  ios/       SwiftUI app. Xcode project is generated by XcodeGen from project.yml.
  android/   Jetpack Compose app (Gradle, AGP 9).
core/        Rust workspace shared by both mobile apps.
  crates/kumo-core/  Pure Rust: Kumospace REST/WS protocol, Sendbird client, sync engine, state.
  crates/kumo-ffi/   UniFFI layer: the only API Swift and Kotlin see (`KumoApp` object). Also builds uniffi-bindgen.
  crates/kumo-cli/   Desktop CLI over the core for testing against the real backend (`kumo-cli --help`).
  crates/kumo-devtools/  Talking to the Kumospace Desktop app over DevTools: page discovery, evaluation, session import. Mac side only; the phones never link it.
scripts/     build-core-ios.sh (XCFramework + Swift bindings), build-core-android.sh (cargo-ndk .so + Kotlin bindings).
docs/        Protocol spec, feature inventory of the official app, this file, roadmap.
```

Generated artifacts are not committed: `apps/ios/KumoCore/`, `apps/ios/Kumowatch.xcodeproj/`,
`apps/android/app/src/main/jniLibs/`, `apps/android/app/src/main/java/uniffi/`. Run the build scripts first.

## What lives where

The rule: everything that talks to a backend, keeps state or makes a decision lives in Rust.
Native code renders, and owns the things that only the OS or a vendor SDK can do.

| Concern | Rust core | Native (Swift / Kotlin) |
|---|---|---|
| Firebase auth | REST `identitytoolkit` sign-in (password, `signInWithIdp`), `securetoken` refresh, token expiry | Google / Microsoft sign-in UI that yields an id token; Keychain / Keystore storage behind a Rust-defined trait |
| Kumospace REST | `api.kumospace.com/v1/*` client, errors, pagination | – |
| Space realtime | `ws.kumospace.com` socket, reconnect state machine, census/entities/zones store, office model (lobby, floors, rooms, common area) | Rendering |
| Chat | Sendbird protocol client (WS `CMD{json}` + REST `/v3`), SQLite cache, background sync via changelogs, unread counts, outgoing queue | Rendering, image picking, markdown display |
| Session (nearby/public) chat | WS `chat` op and `notification` handling | Rendering, message sound |
| Calls | The Call session for both Call sources: credentials, Handoff and the Lease, retries and token-problem classification, Zone mates, subscriptions, tiles, speaking and active speaker | Daily iOS / Android SDK behind the `CallMedia` trait (join / leave / inputs / subscriptions, track handles), rendering, audio routing, foreground service, reacting to the phase |
| Push | Sendbird push-token registration, payload parsing into a route | APNs / FCM receipt, notification display, background wake-ups that call Rust sync |
| Relay (Mac) | Relay client for every route, pairing, typed Desktop state, viewport framing, tap / go-to decisions, Availability and presence labels, polling while watched | Rendering, presence colours, pairing storage behind a Rust-defined trait (Keychain + widget app group / Keystore) |

## Core modules (kumo-core)

- `auth`: Firebase REST (password, custom token, refresh), `SessionStore` trait, `Auth` with a sync snapshot.
- `client`: Kumospace REST (`KumoApi`), including `mint_login_token` for session transfer.
- `space_socket`, `ws`: ws.kumospace.com connection and protocol types.
- `sendbird`: frame codec, socket task (LOGI, PING/PONG, acks by `req_id`, events), REST client.
- `desktop`: the Relay ↔ phone protocol. Typed Desktop state (`DesktopState`, converted from the Desktop app's page
  script by `from_page`), `Presence` / `Availability` labels, viewport framing, the route list, request / reply types,
  `RelayError`, and `RelayClient` (reqwest) used by the phones and by kumo-relay's integration tests.
- `call`: the Call session. `CallMachine` is pure (inputs in, effects out; timers are `Schedule` effects); `CallSession`
  drives it against four ports: `MediaPort` (Daily), `OfficeCallSource` (the phone's own Office connection),
  `RelayCalls` (Handoff, Lease renewal every 10 s, Reclaim, Desktop Zone mates polled every 3 s; `RelayCallSource` is the
  real one over `RelayClient`) and `CallChanges`. Media events carry the attempt they belong to, so anything from an old
  attempt is dropped. Token problems and unexpected drops leave Daily, back off 1 / 2 / 3 s and refresh (Office) or hand
  off again (Desktop); a stale Lease fails the call as taken over without a Reclaim.
- `app_session`: `AppSession` owns at most one Call session and tears the old one down (Reclaim or Office leave) before
  starting another.
- `chat`: `ChatStore` (SQLite, versioned migrations via `PRAGMA user_version`), `ChatEngine` (sync, prefetch, live events,
  outbox), `ChatTransport` (the engine's only network seam; `SendbirdTransport` is the real Sendbird + Kumospace
  adapter, tests use a scripted fake), `markdown`, UI row models.

## FFI shape

- UniFFI proc-macros in `kumo-ffi`; Swift and Kotlin bindings are generated in library mode from the built library.
- One `uniffi::Object`, `KumoApp`, owns a Tokio runtime. Async methods run on it; sync methods only read SQLite.
- Rust pushes invalidation events through the foreign `AppListener` (`ChannelsChanged`, `MessagesChanged{url}`,
  `Typing`, `Connection`, `Error`); the UI then reads fresh rows synchronously (`channels()`, `messages(url, limit)`),
  which takes a few milliseconds. The UI never polls.
- Session storage comes in as the foreign `SecureStorage` trait (Android Keystore, iOS Keychain).
- `KumoApp.relay_client()` returns the `RelayClient` object for the Relay on the office computer. Its pairing comes in as the foreign
  `RelayStorage` trait. The UI calls `watch_desktop()` / `unwatch_desktop()` while Desktop state is on screen; Rust polls
  every 3 s only while watched, emits `DesktopChanged`, and the UI reads `desktop()` synchronously.
- Calls: `join_call()` (Office, current Zone; `join_room` / `join_person` start it implicitly), `handoff_call()`
  (Desktop), `set_mic`, `set_camera`, `leave_call()` (idempotent, Reclaims a Desktop call) and the synchronous
  `call() -> CallView`. Rust emits `CallChanged` only when the `CallView` changes. Daily comes in as the foreign
  `CallMedia` trait, whose `join` receives a `CallMediaSink` stamped with the attempt; native forwards Daily callbacks to
  it (always the full participant list) and keeps only a participant id → tracks map for rendering.
- Relay Lease: `POST /v1/desktop/handoff` returns a `lease_id`; phones renew it on `POST /v1/desktop/lease` (409 when a
  newer Handoff made it stale) and Reclaim with it. The Relay Reclaims 45 s after the last renewal and on shutdown.
- Relay notification kinds: the Relay delivers an Alert only when Mirroring (`PUT /v1/enabled`) is on and the
  `NotificationProfile` allows the kind for the current `MyStatus` (Available / Away / Focusing from the Desktop app's own
  Availability; Unknown when the Desktop app is not connected, its state can't be read, or the user is idle or offline).
  `PUT /v1/notifications` merges `{status, kinds}` (one status), `{available?, away?, focusing?, unknown?}` (a profile)
  or an older flat kinds body (every status). The profile lives in the Relay's `state.json`; a missing kind or status
  means on (except `floor_entries`, which means off), and an older flat file or `RelayStatus` counts as the same kinds for every status. `RelayStatus` carries
  `notifications` and `my_status`. Phones call `RelayClient.set_notification_kinds(status, kinds)`.
- Open chat silences its own Alerts: the phone decides whether to show an Alert for the chat on screen. Android
  "This phone" drops it in the core (`channel_is_open`); iOS drops an APNs push for `AppModel.visibleChannel` in
  `willPresent`. ntfy is shown by the ntfy app, so the phone can't decide there; as a temporary workaround the phone
  reports the chat on screen (`KumoApp.open_channel` / `close_channel` / `set_foreground`) with
  `PUT /v1/viewing {channel_url}` every 10 s, `null` on close or background, and the Relay skips ntfy for that chat
  for 30 s after the last report (`kumo-relay/src/viewing.rs`). An older Relay answers 404 and nothing changes, so
  `RELAY_API` stays. Remove `/v1/viewing` once the iOS app has Apple's notification filtering entitlement
  (`com.apple.developer.usernotifications.filtering`) and every device decides for itself.
- Relay version check: `RelayStatus` carries `api` (the Relay API number, `RELAY_API`; a Relay without it speaks API 1)
  and `version` (the Better Kumo / kumo-relay version). Bump `RELAY_API` whenever an older Relay would reject or
  misread what a newer phone sends. API 2 adds Desktop Nearby Chat (`/v1/desktop/nearby-chat`). Phones compare it with their own `RELAY_API`: an older Relay shows "update Better
  Kumo on the computer", a newer one shows "update the app" (`relay_compatibility_note`).
- Phone delivery (Android "This phone"): `PhoneMirroring` filters local Alerts by the same profile, using `MyStatus` from
  the phone's own Office connection. `KumoApp.apply_notification_kinds` saves locally and, when paired, sends to the
  Relay; a change the Relay didn't get stays pending and `sync_notification_profile` pushes it instead of adopting the
  Relay's profile.
- Chat sending: `send_message(channel_url, text, files, parent_id)` is the only send path. The engine writes the
  Outbox batch (each file as a pending `FILE` row whose bytes live in SQLite, then the text) and delivers it in order;
  the first failure marks the rest failed, and `retry_message(local_id)` on any failed row resends what is left of the
  batch. `attachment_limits()` gives both apps the same count (10), max image side (1600 px) and JPEG quality (85);
  decoding and re-encoding stay native. Pending image rows have no URL yet; the apps show the thumbnail they picked.
- File URLs: `MessageItem.file_url` already carries `?auth=<ekey>` when Sendbird needs it (`authorized_file_url`, the one
  place that knows the key). The engine re-emits `MessagesChanged` for the open channel when the key changes, so rows
  read before LOGI are re-read. Apps key their image caches by the URL without `auth`.
- Platform services Rust needs (secure storage, current time zone, network reachability) come in as foreign traits
  implemented in Swift / Kotlin.

## Why chat will be fast

The official app's slowness comes from specific choices (see `kumospace-features.md` §4): a 2 MB WebView composer per
screen, channel lists re-fetched from the network on every incoming message, REST-based unread counts refreshed on every
foreground, and an unvirtualized list. The rewrite inverts those:

1. Local-first: every screen reads from SQLite in Rust first and renders immediately; network only fills gaps.
2. Incremental sync: Sendbird channel and message changelogs (`/my_group_channels/changelogs`,
   `/messages/changelogs`) with stored sync tokens, so resume costs one small request, not a full re-pagination.
3. Background prefetch: after connect and on push / background refresh, the latest page of each recent channel is
   pulled into the cache, so opening a channel never waits and never needs scrolling to trigger loading.
4. Live updates from the Sendbird socket are applied to the store and emitted as diffs.
5. Native composer (UITextView / BasicTextField) and virtualized lists (List / LazyColumn).

## Trust boundaries

- The Firebase web API key and the Sendbird app id are public client identifiers shipped inside the official app.
- Tokens (Firebase refresh token, Sendbird session token) never leave the device and are stored only via the
  platform secure-storage trait.
