# Architecture

## Repository layout

```
apps/
  watcher/   Node service: listens to the Kumospace desktop app over CDP and reacts (ntfy). Runs on the Mac via launchd.
  ios/       SwiftUI app. Xcode project is generated by XcodeGen from project.yml.
  android/   Jetpack Compose app (Gradle, AGP 9).
core/        Rust workspace shared by both mobile apps.
  crates/kumo-core/  Pure Rust: Kumospace REST/WS protocol, Sendbird client, sync engine, state.
  crates/kumo-ffi/   UniFFI layer: the only API Swift and Kotlin see (`KumoApp` object). Also builds uniffi-bindgen.
  crates/kumo-cli/   Desktop CLI over the core for testing against the real backend (`kumo-cli --help`).
scripts/     build-core-ios.sh (XCFramework + Swift bindings), build-core-android.sh (cargo-ndk .so + Kotlin bindings).
docs/        Protocol spec, feature inventory of the official app, this file, roadmap.
```

Generated artifacts are not committed: `apps/ios/KumoCore/`, `apps/ios/Kumowatch.xcodeproj/`,
`apps/android/app/src/main/jniLibs/`, `apps/android/app/src/main/java/uniffi/`. Run the build scripts first.

## What lives where

The rule: everything that talks to a backend, keeps state or makes a decision lives in Rust.
Native code renders, and owns the things that only the OS or a vendor SDK can do.

| Concern | Rust core | Native (Swift / Kotlin) |
|---|---|---|
| Firebase auth | REST `identitytoolkit` sign-in (password, `signInWithIdp`), `securetoken` refresh, token expiry | Google / Microsoft sign-in UI that yields an id token; Keychain / Keystore storage behind a Rust-defined trait |
| Kumospace REST | `api.kumospace.com/v1/*` client, errors, pagination | – |
| Space realtime | `ws.kumospace.com` socket, reconnect state machine, census/entities/zones store, office model (lobby, floors, rooms, common area) | Rendering |
| Chat | Sendbird protocol client (WS `CMD{json}` + REST `/v3`), SQLite cache, background sync via changelogs, unread counts, outgoing queue | Rendering, image picking, markdown display |
| Session (nearby/public) chat | WS `chat` op and `notification` handling | Rendering, message sound |
| Calls | Daily credentials from the WS `room` frame, token refresh, call state | Daily iOS / Android SDK (video, audio routing, PiP, CallKit / foreground service) |
| Push | Sendbird push-token registration, payload parsing into a route | APNs / FCM receipt, notification display, background wake-ups that call Rust sync |

## Core modules (kumo-core)

- `auth`: Firebase REST (password, custom token, refresh), `SessionStore` trait, `Auth` with a sync snapshot.
- `client`: Kumospace REST (`KumoApi`), including `mint_login_token` for session transfer.
- `space_socket`, `ws`: ws.kumospace.com connection and protocol types.
- `sendbird`: frame codec, socket task (LOGI, PING/PONG, acks by `req_id`, events), REST client.
- `chat`: `ChatStore` (SQLite), `ChatEngine` (sync, prefetch, live events, outbox), `markdown`, UI row models.

## FFI shape

- UniFFI proc-macros in `kumo-ffi`; Swift and Kotlin bindings are generated in library mode from the built library.
- One `uniffi::Object`, `KumoApp`, owns a Tokio runtime. Async methods run on it; sync methods only read SQLite.
- Rust pushes invalidation events through the foreign `AppListener` (`ChannelsChanged`, `MessagesChanged{url}`,
  `Typing`, `Connection`, `Error`); the UI then reads fresh rows synchronously (`channels()`, `messages(url, limit)`),
  which takes a few milliseconds. The UI never polls.
- Session storage comes in as the foreign `SecureStorage` trait (Android Keystore, iOS Keychain).
- Platform services Rust needs (secure storage, current time zone, network reachability) come in as foreign traits
  implemented in Swift / Kotlin.

## Why chat will be fast

The official app's slowness comes from specific choices (see `kumospace-features.md` §4): a 2 MB WebView composer per
screen, channel lists re-fetched from the network on every incoming message, REST-based unread counts refreshed on every
foreground, and an unvirtualized list. The rewrite inverts those:

1. Local-first: every screen reads from SQLite in Rust first and renders immediately; network only fills gaps.
2. Incremental sync: Sendbird channel and message changelogs (`/my_group_channels/changelogs`,
   `/messages/changelogs`) with stored sync tokens, so resume costs one small request, not a full re-pagination.
3. Background prefetch: after connect and on push / background refresh, the latest page of each recent channel is
   pulled into the cache, so opening a channel never waits and never needs scrolling to trigger loading.
4. Live updates from the Sendbird socket are applied to the store and emitted as diffs.
5. Native composer (UITextView / BasicTextField) and virtualized lists (List / LazyColumn).

## Trust boundaries

- The Firebase web API key and the Sendbird app id are public client identifiers shipped inside the official app.
- Tokens (Firebase refresh token, Sendbird session token) never leave the device and are stored only via the
  platform secure-storage trait.
